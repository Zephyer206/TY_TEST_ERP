# source-command-speckit-checklist

Use this skill when the user asks to run the migrated source command `speckit.checklist`.

## Command Template

# Speckit Checklist — 需求质量检查清单

为当前功能生成需求质量检查清单（"英文的单元测试"）。

## 核心概念

检查清单验证的是需求**质量**，而非代码是否正常。

**不是代码测试：**
- "验证按钮点击正常"
- "测试错误处理是否有效"
- "确认 API 返回 200"

**是需求质量测试：**
- "视觉层次要求是否有可衡量的具体标准？[清晰性]"
- "'显著展示'是否有可衡量的属性定义？[歧义]"
- "悬停状态要求在所有元素中是否一致？[一致性]"
- "图片加载失败时的回退行为是否已定义？[边界情况]"

## 前置条件

- `specs/<feature>/spec.md`
- 可选：plan.md、tasks.md

## 工作流程

### 1. 初始化

从仓库根目录运行 `.specify/scripts/powershell/check-prerequisites.ps1 -Json` 获取 FEATURE_DIR。

### 2. 澄清问题（动态生成）

从用户请求中衍生最多 3 个情境化澄清问题：

- 范围细化："这是否应包含与 X、Y 的集成触点？"
- 风险排序："哪些风险领域需要强制门控检查？"
- 深度校准："轻量级预提交检查表还是正式发布门控？"
- 受众："仅作者使用还是 PR 审查时同行使用？"

如参数中已清晰则跳过。

### 3. 生成检查清单

创建 `FEATURE_DIR/checklists/<领域>.md`，领域名简短描述性：

**文件名示例**：`ux.md`、`api.md`、`security.md`、`performance.md`

**文件处理**：
- 文件不存在 → 新建，ID 从 CHK001 开始
- 文件存在 → 追加新条目，ID 接续上一个
- 绝不删除或替换现有内容

### 4. 分类结构

按质量维度分组：

- **需求完整性** — 所有必要需求是否已记录？
- **需求清晰性** — 需求是否具体明确、无歧义？
- **需求一致性** — 需求是否相互一致无冲突？
- **验收标准质量** — 成功标准是否可衡量？
- **场景覆盖** — 所有流程/场景是否已覆盖？
- **边界情况覆盖** — 边界条件是否已定义？
- **非功能性需求** — 性能、安全、无障碍是否已指定？
- **依赖与假设** — 是否已记录并验证？
- **歧义与冲突** — 哪些需要澄清？

### 5. 条目格式（强制）

每条遵循：

```
- [ ] CHK001 [场景] 的 [需求类型] 是否已定义？[完整性]
- [ ] CHK002 [模糊术语] 是否有可衡量的具体标准？[清晰性, Spec §FR-1]
- [ ] [章节A] 和 [章节B] 的需求是否一致？[一致性]
```

- 以问句形式询问需求质量
- 括号内标注质量维度
- 适时引用规格章节 `[Spec §X.Y]`
- 用 `[Gap]` 标记缺失的需求

### 6. 可追溯性

- 至少 80% 条目必须包含可追溯性引用
- 使用 `[Spec §X.Y]`、`[Gap]`、`[Ambiguity]`、`[Conflict]`、`[Assumption]` 标记

### 7. 反模式（禁止）

❌ 以"验证"、"测试"、"确认" + 实现行为开头
❌ 引用代码执行、用户动作、系统行为
❌ "显示正常"、"工作正常"、"按预期运行"
❌ "点击"、"导航"、"渲染"、"加载"、"执行"
❌ 测试用例、测试计划、QA 流程
