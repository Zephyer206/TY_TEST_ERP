# 客户与客户零件导入完整性审计报告

审计时间：2026-07-13 21:15（Asia/Hong_Kong）  
审计对象：当前 PostgreSQL 数据库与 `excel/五金模具及产品清单表.xls`  
审计方式：数据库连接强制只读；本次未修改客户、零件、模具或关联数据。

## 1. 结论

当前客户及客户零件关联导入 **不完整，也存在实际归错客户的情况**，不能认定为符合设计。

- 客户表共 178 条，其中可识别的规范客户 95 条。
- 确定有 3 条英文缩写被截断生成的错误空壳客户。
- 另有 57 条由 Excel Sheet 名直接生成的高置信空壳/重复客户，其中包括 `60T 连续模`；它不是客户。
- 还有 23 条零引用客户证据不足，只能列为待人工确认，不能自动删除或合并。
- Excel 与 staging 中应存在 5,078 个唯一客户—内部零件—客户件号映射；当前仅正确建立 4,588 个，缺失 490 个，涉及 41 个客户。
- 551 条 staging 记录的 `resolved_alias_id` 指向同一客户、同一客户件号下的错误内部零件。
- 发现 1 组真实客户归属碰撞：武汉客户的 36 行、34 个零件被归到苏州客户。

## 5. 实际归错客户：武汉被并入苏州

这是本次最明确的“零件归到错误客户”问题：

- 规范化后使用的数据库客户：id=7272，`日立安斯泰莫底盘系统（苏州）有限公司`。
- 同一 customer_id 下总计 175 行、155 个唯一零件。
- 其中真正属于 `日立安斯泰莫底盘系统（武汉）有限公司` 的有 36 行、34 个唯一零件。
- 因此需要拆分的是 34 个武汉客户零件，不是把该 customer_id 下全部 155 个零件迁走。

根因是 `backend/scripts/import_staged_authoritative.py:59` 和 recovery 脚本中的客户名称规范化会删除括号内全部内容。删除“（武汉）/（苏州）”后，两家公司被归一成同一个名称。

`温州力邦企业` → `温州力邦企业有限公司` 属于可接受的公司后缀补全，不属于地点碰撞。

## 6. 缺失 490 个零件关联的根因

数据库当前唯一索引为：

```sql
UNIQUE (customer_id, customer_part_no, revision)
```

它没有包含 `part_id`。Excel 实际存在同一客户件号对应多个内部零件/多副模具的情况，因此第二个内部零件关联会被唯一索引阻止。

恢复导入脚本也会在发现“同一客户 + 同一客户件号，但 part_id 不同”时直接返回已有 alias，并打印 `SKIP`。这同时造成：

- 490 个合法映射未建立；
- 551 条 staging 的 `resolved_alias_id` 指向另一个内部零件；
- 前端按客户查零件或后续按客户查价格时漏项/串项。

相关位置：

- `backend/scripts/migrations/008_authoritative_schema.py:323`
- `backend/scripts/import_staged_recovery.py:225-240`
- `backend/scripts/import_staged_authoritative.py:59`

## 7. 修复边界与建议顺序

当前只完成审计，没有修改数据库。后续修复必须分段执行：

1. 先统一设计：客户零件 alias 唯一性应包含 `part_id`；客户名称规范化必须保留地点限定词。
2. 做完整数据库备份，并生成 490 个缺失 alias 的 dry-run 清单；冲突只报告，不覆盖。
3. 单独拆分武汉/苏州数据，只迁移已确认的 36 行、34 个武汉零件。
4. 合并或停用 3 条英文截断空壳和 57 条高置信 Sheet 空壳；23 条低置信客户不自动处理。
5. 全量 SELECT 复核：5,078/5,078 映射匹配、alias part_id 错位为 0、武汉/苏州碰撞为 0。
6. 最后使用浏览器 MCP 验收客户下拉、按客户查零件、零件详情客户/模具关联和客户价格查询。
