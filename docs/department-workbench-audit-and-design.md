# 各部门工作台现状审查与设计方案

日期：2026-10-18（Asia/Shanghai）  
状态：设计草案；现状已核查，组织归属与具体审批额度待业务确认。  
交付：本文件＋[可交互工作台原型](design/department-workbenches.html)。原型使用虚构示例，不读写业务数据。

## 1. 审查结论

**部门职责在原规格中有定义，当前系统尚未形成完整的部门工作台与交接闭环。**

现状是一个共用工作台、两个业务待办来源和四个岗位队列。不能把现有菜单按模块分组等同于部门职责已经落地，也不能把目录中存在 Vue 文件等同于该功能可以使用。

| 检查项 | 已核实的情况 | 判断 |
| --- | --- | --- |
| 工作台入口 | `/workbench` 包含“老板总览”和“岗位待办”；所有普通岗位使用同一 TaskWorkbench | 共用框架可保留，缺少各部门内容配置 |
| 真实待办来源 | `TaskModule` 仅有 production、shipping；服务仅加载生产计划和发货订单 | 开发、检验、喷涂、包装、设备等业务尚未汇总 |
| 岗位队列 | materials、scheduling、label、shipping 四种 | 只覆盖部分生产准备及发货环节 |
| 分工匹配 | 工作台通过 dept/position 的字符串关键词决定队列；warehouse 同时获得标签与发货队列 | 缺少稳定的岗位能力与范围授权；标签与发货边界不清 |
| 事项归属 | 工作台只有岗位名称，无结构化责任部门、受理人、前序/后序、阻塞原因 | 能看到事项，尚不足以明确追责及交接 |
| 业务归属 | 发货跟进使用 created_by；取消申请的业务身份在服务中存在非标签人员默认视为 business 的逻辑 | 创建人不能普遍替代正式业务负责人；身份应显式判定 |
| 页面入口 | 机台执行、工艺流转、全检与包装、后处理为禁用菜单 | 生产执行链条未全部开放 |
| 存量页面 | coating、packaging、machines、materials/batches、materials/slitting、sampling 有源文件，但当前 router 未注册相应入口 | 部分可复用，需逐项修复与浏览器验收后启用 |
| 品管页面 | `views/quality/index.vue` 是 T/W/P 等数据质量演示，不是首件/巡检/OQC 工作台 | 数据治理与产品质量应分开 |
| 开发页面 | 项目样件、图纸变更中存在静态数据与预留动作；研发合规明确为浏览器演示台账 | 不能作为开发、文控、财务闭环已完成的依据 |
| 不良品 | 已有服务端按品管、开发、生产、业务划分的动作权限与流程 | 是跨部门协作基础，尚未接入共用工作台 |
| 老板总览 | 页面提示布局预览、2026-10-17 示例日期；数据来自 bossPreviewData | 经营指标尚非实时业务统计 |
| 登录与权限 | 前端固定管理员验收身份；通用权限主要按 LV1–LV4 判断；工作台未使用管理员有效切换身份来构建队列 | 真实部门隔离尚未验收 |
| 财务/人事 | 当前路由及模块目录未发现完整的对应业务工作台 | 设计占位；需要业务数据源和岗位规则后建设 |

## 2. 组织、岗位与权限设计

以原规格的十个业务部门为基线，另设老板和系统管理员两个工作视角。资材采购暂按原料仓库内的职能设计；标签、成品收发暂按全检部内的岗位设计。这是工作视角划分，正式组织归属需要业务确认；同一人可以兼岗。

每条任务必须明确：**一个责任部门、一个处理岗位、当前受理人或“待认领”、完成条件、下一责任岗位。** 协作部门可以有多个，当前主责只有一个。

| 部门/视角 | 本部门负责 | 主要待办 | 完成与交付结果 | 边界 |
| --- | --- | --- | --- | --- |
| 业务部 | 客户、询报价商务部分、订单需求与交期、客户样件确认、客户反馈、交付协调 | 待补询价、待提交审批、待客户确认、交期风险、取消申请确认 | 需求/商务条件完整并获所需批准；客户结论有记录；交付需求交生产/发货岗位 | 技术结论交开发；实物发货交发货岗；质量放行交品管 |
| 开发部 | 技术可行性、图纸版本、T/W/P 与工艺、模具开发维修、样件试制、返工方案 | 待技术评审、待补工艺、模具节点、试模整改、返工准备、变更影响评估 | 有效图纸/工艺/模具及验证记录具备；方案交生产，验证交品管，客户确认交业务 | 不代客户确认，不独立决定量产质量放行 |
| 原料仓库·资材采购岗 | 需求核料、缺料分析、采购/外协跟催、到料承诺 | 待物料确认、缺料、采购交期异常、外协交接 | 核定可用物料与预计可用日；缺料原因和补料计划明确 | “在途”不能记为“可用”；实物收料及检验由对应岗位记录 |
| 原料仓库·收发岗 | 到料登记、批次库位、待检隔离、分条、领退料、盘点 | 待收货、待送检、待上架、待分条、待领退料、差异待核 | 合格批次可追溯，收发数量与库位记录完整 | 仓库执行隔离与收发，品管给出检验结论 |
| 生产部 | 计划转化、排产、机台调度、班组任务、开工报工、工序交接 | 待排产、待开工、首件等待、在制异常、待报工、返工执行 | 合格/不良/返工数量及工序记录完整；转下一实际工序 | 开工服从物料/模具/工艺/设备及首件门槛；不自行放行质量异常 |
| 品管部 | 检验标准、IQC、首件、巡检、OQC、不良品确认与验收、质量放行 | 待检、待判定、待复检、待不良品确认、返工验收、放行核对 | 有检验记录、数量及结论；合格放行，不合格进入受控处置 | 全检作业与品管判定区分；质量结论不得由业务交期自动覆盖 |
| 全检部·全检包装岗 | 按标准全检挑选、包装、装箱、包材/数量/箱号核对 | 待全检、待包装、包装异常、待入库移交 | 全检结果与箱包记录完整；合格品移交成品收发岗 | 执行作业不替代品管 OQC；发现不良交品管判定 |
| 全检部·标签岗 | 客户标签版本、件号、数量、箱号及订单匹配确认；取消申请标签侧确认 | 待标签确认、标签变更、取消协同确认 | 留存已确认版本和确认人；交发货岗核对 | 标签确认不代表已出库或已发货；岗位能力独立配置 |
| 全检部·成品收发岗 | 合格成品收货、库位库存、备货、实物出库、发运与物流记录 | 待入库、待备货、待发货、数量差异、物流待补 | 实发明细、库存事件和物流记录一致；回传业务与会计 | 订单已提交/已贴标签不能等同于实际发出 |
| 喷涂部 | 喷涂/回火等后处理作业、工艺配方执行、批次报工、异常上报 | 待接收、待开工、在制、待交接、返工 | 按工艺记录处理批次与合格/不良数量；送品管或全检包装 | 仅实际需要该工序的产品进入；不能统一强插喷涂环节 |
| 设备部 | 设备台账、故障报修、维护计划、维修与复机交接 | 待报修受理、维修中、到期保养、复机待确认 | 维修/保养记录及恢复状态完整；生产收到可用状态 | 设备恢复不直接将生产计划记为完成 |
| 会计部 | 应收应付、对账、成本复核、财务凭证、研发费用证据核对 | 待对账、差异待核、凭证待补、研发费用待复核 | 业务单据与核算记录可追溯；差异关闭 | 不以创建财务记录替代实物出入库；人事薪酬等信息按授权范围 |
| 人事部 | 人员/岗位资料、入转调离、考勤异常、培训资质 | 资料待补、考勤待核、岗位调整、资质到期 | 有效人员、岗位与资质信息交对应管理流程 | 人事提出岗位变更，系统管理员按获批授权配置；不直接获得业务审批权 |
| 老板 | 报价终审、经营风险、交付与开发协调、获授权的例外决策 | 待审批、交付风险、开发延期、质量影响、跨部门阻塞 | 审批有依据、协调有责任人和期限；执行回原责任部门 | 汇总指标可穿透原单；未接入数据必须标注，例外也保留审计 |
| 系统管理员 | 用户与能力配置、基础字典、接口/通知运行、审计、部门视角排障 | 授权待配置、无人接收任务、同步异常、审计异常 | 配置有来源和审计；恢复任务投递 | 系统管理身份不自动获得老板商务终审权；部门预览遵从有效身份 |

### 需要业务确认的四个组织点

1. 资材采购是否独立部门，还是归原料仓库/生产管理；设计中的队列可以保持不变。
2. 标签、成品仓库、发货在现组织中归全检部还是独立仓储部门；允许兼岗，但每个动作分别留痕。
3. 品管 IQC 与仓库收货的实际人员配置；收货登记和合格判定保持两个不同动作。
4. 报价、报废、库存调整、采购、费用等例外的具体审批人和额度；本方案不虚构数值。

## 3. 跨部门交接规则

主流程按实际工艺路线选择工序：

```mermaid
flowchart LR
  A[业务：完整需求] --> B[开发：技术与模具就绪]
  A --> C[资材：物料就绪]
  B --> D[生产：排产与开工准备]
  C --> D
  D --> E[品管：首件判定]
  E --> F[生产：执行与报工]
  F --> G{实际工艺路线}
  G --> H[喷涂：后处理]
  G --> I[全检：全检包装]
  H --> I
  I --> J[品管：所需出货检验]
  J --> K[成品收发：备货]
  K --> L[标签：确认版本与订单]
  L --> M[发货：实发及物流]
  M --> N[业务跟进 / 会计对账]
```

此图表示责任交接；检验节点是否适用由工艺与质量规则决定。无喷涂产品跳过喷涂，不得通过图中简化箭头跳过实际工序。首件未放行时，允许准备/试制的范围由现行业务规则定义。

| 流程 | 当前主责与交出物 | 下游收到什么 | 不满足条件时 |
| --- | --- | --- | --- |
| 询价→报价 | 业务补齐需求，开发完成技术部分，业务提交商务方案 | 老板收到完整审批单 | 退回具体缺项及责任岗，不把同一任务同时派给所有人 |
| 需求→排产 | 业务给交期/数量，开发给有效工艺模具，资材给物料可用信息 | 生产主管收到具备条件的计划 | 在生产工作台显示“等待前序”；缺项成为对应部门可办理任务 |
| 工序→工序 | 本工序完成指定数量、质量、批次与流转记录 | 下游收到实际可接收数量及证据 | 拒收有原因、数量和责任人，原任务重新进入待处理 |
| 不良品处置 | 品管确认→开发准备适用方案/模具→指定岗位执行→品管逐项验收 | 验收后按处置结果进入库存/后续工序 | 保留原单与步骤顺序；验收失败重新进入对应步骤，不提前关闭 |
| 标签→发货 | 标签岗确认版本及订单；品管及库存门槛满足 | 发货岗收到可发明细 | 门槛不足标记阻塞原因；不得直接改为完成 |
| 取消申请 | 按现有流程收集业务侧与标签侧的确认 | 业务单服务更新剩余需求与相关占用 | 待确认期间按现行规则冻结相关发运；工作台只展示流程结果 |
| 设备故障→复机 | 设备给维修记录与恢复状态 | 生产接收复机信息并安排剩余任务 | 故障影响展示到关联机台/计划，不自动重排全部计划 |

每次交接记录：原单、批次/明细、来源部门、接收岗位、数量、资料版本、提交人、提交时间、要求完成时间、受理/拒收结果。部分完成只移交已通过门槛的数量。

## 4. 共用页面结构

采用现有克制的工业工作台风格：中性色面板、语义状态色、紧凑表格、清晰行操作。延续项目现有 CSS token 与 Element Plus；技能检索建议仅作参考，不覆盖现有设计系统。各部门复用页面骨架，配置职责、任务类型、指标与快捷动作。

```text
当前公司 / 部门 / 岗位 / 数据更新时间                业务主动作
本岗职责一句话       接收：上游岗位 → 交付：下游岗位

待处理           今日到期           已逾期           等待前序

我的待办  |  岗位待办  |  我发起的             部门职责说明
搜索 / 事项类型 / 截止时间 / 阻塞状态

优先级  原单/产品  当前事项  主责/受理人  完成期限  阻塞原因  操作
...

交接详情：前序完成证据 → 当前完成条件 → 下一接收岗位
```

| 区域 | 设计要求 |
| --- | --- |
| 部门/岗位识别 | 显示服务端有效身份；普通用户只看获授权岗位。原型中的自由切换仅用于设计评审 |
| 四类数量 | 待处理=当前可办理未完成事项；今日/逾期按任务截止时间；等待前序独立统计。四卡并非相加关系，今日和逾期属于待处理子集 |
| 我的待办 | 明确指派/认领给本人的任务及本人草稿，不把创建人自动视为所有后续步骤的处理人 |
| 岗位待办 | 当前有效岗位的共享队列；显示受理人或待认领。无认领能力的现有模块先明确显示“岗位共享，未指派” |
| 我发起的 | 展示当前进度、当前主责与催办上下文；不因此获得下游办理权限 |
| 行操作 | 每项只突出当前可做的主要动作；深链进入原业务页及具体单据/明细 |
| 完成条件 | 详情给出必需资料、数量、前序门槛和下一岗位。完成必须由原业务服务成功后派生 |
| 角色差异 | 主管增加部门负荷、待认领及调度；员工优先本人/本机台；老板展示审批和全公司风险；管理员展示配置与投递异常 |
| 统计与真实数据 | 区分业务数据、未接入、加载失败、无任务；未接入不能显示“0”或“全部完成” |
| 失败与并发 | 可重试且保留筛选；防重复提交。任务过期或被他人完成时刷新到当前状态，不能覆盖已更新版本 |
| 响应式与可访问性 | 桌面紧凑表格；窄屏按卡片保留事项/期限/动作；有键盘焦点、文字状态、对话框关闭与空态说明 |

## 5. 数据与权限落地约束

1. 保留现有 `workbench.list` 与原业务单据为事实来源，增加部门任务投影；不要再造一套可任意改状态的“工作台业务流程”。
2. 建议任务投影包含：task_key、source_type/source_id/source_line_id、step_key、company_id、owner_department、owner_role、assignee_id、status、due_at、blocked_reason、upstream/next_role、completion_requirements、source_revision、route/action。稳定键由原单明细与步骤生成，避免重复任务和重复统计。

## 6. 建设顺序与验收标准

| 阶段 | 交付内容 | 独立通过条件 |

| C 已有流程接入 | 业务、开发、不良品、生产、资材、品管、全检包装、喷涂、发货逐项接入 | 每个节点有主责、完成条件和下一岗位；原业务完成后待办消失；部分完成数量正确 |
