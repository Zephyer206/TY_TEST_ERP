# Feature Specification: 发货订单业务流程

**Feature Branch**: `007-shipping-order-flow`  
**Created**: 2026-08-22  
**Status**: Draft  
**Input**: 用户确认的正式订单、样件订单、标签确认、分批发货和物流记录业务流程

## User Scenarios & Testing

### User Story 1 - 业务创建订单（Priority: P1）

业务人员为客户建立正式订单或样件订单。订单可以包含多个零件，同一 PO 中同一客户件号也可以重复为多条明细，以分别安排不同的计划发货日期。

**Why this priority**: 订单是后续全检、标签和发货的业务入口，必须先保证客户需求和每次计划发货被准确记录。

**Independent Test**: 业务人员可以创建一张包含多条明细的订单，保存草稿、提交订单，并在订单详情中看到完整的客户件号、零件名称、数量、计划发货日期和备注。

**Acceptance Scenarios**:

1. **Given** 业务人员新建订单，**When** 未切换订单类型，**Then** 订单默认为正式订单。
2. **Given** 业务人员选择正式订单，**When** 填写客户、PO 号和至少一条完整明细并提交，**Then** 订单提交成功并进入后续处理状态。
3. **Given** 一张 PO 需要分批发同一个客户件号，**When** 业务人员新增两条相同客户件号的明细并填写不同数量和日期，**Then** 系统保留两条独立明细。
4. **Given** 业务人员已选择客户，**When** 在客户件号输入框输入部分字符（例如 `399`），**Then** 系统只展示该客户相关且包含该字符的候选件号；业务人员可以用下拉选择或 Tab 补全，但系统不自动选中。
5. **Given** 客户件号查询不到零件档案记录，**When** 业务人员提交订单，**Then** 系统提示“该客户件号在零件档案中找不到”，并由业务人员决定取消提交或继续提交；继续提交时保留原始件号。

### User Story 2 - 样件订单线下处理并确认标签（Priority: P1）

业务人员可以把订单类型切换为样件。样件不要求 PO 号，不进入全检和系统拣货流程，由专人线下拣货后交给标签人员确认。

**Why this priority**: 样件和正式订单的前置作业不同，但仍需进入统一的订单和发货记录，避免样件交付失去追踪。

**Independent Test**: 业务人员创建样件订单，使用临时客户名称，提交后订单进入待发货；专人线下拣货，标签人员查看明细并确认后，仓库可以继续确认发货。

**Acceptance Scenarios**:

1. **Given** 业务人员选择样件订单，**When** 未填写 PO 号但填写客户或临时客户和完整明细并提交，**Then** 系统允许提交并将订单标记为样件。
2. **Given** 样件客户不存在正式客户档案，**When** 业务人员填写临时客户名称并提交，**Then** 系统允许保存该临时客户名称，且不自动创建正式客户档案。
3. **Given** 样件订单已提交，**When** 专人完成线下拣货并将订单交给标签人员，**Then** 订单不生成全检任务，也不要求系统扫描包装号。
4. **Given** 标签人员完成某些样件明细，**When** 标签人员按明细确认，**Then** 已确认明细进入待发货，未确认明细保持未完成状态。

### User Story 3 - 标签确认与订单锁定（Priority: P1）

标签人员根据订单明细完成标签工作并逐行确认。正式订单在完成必要的前置处理后进入标签环节；已包装且已全检合格的成品库存可以直接进入标签/待发货路径，不重复全检。标签打印内容和独立标签流程不属于本规格。

**Why this priority**: 标签确认是仓库可以发货的业务前置，也是判断订单能否撤回或取消的关键节点。

**Independent Test**: 标签人员可以查看已提交订单明细、逐行确认部分明细；已确认明细允许仓库发货，未确认明细不能被误认为已完成标签。

**Acceptance Scenarios**:

1. **Given** 订单存在多条明细，**When** 标签人员只确认其中一部分，**Then** 系统只将已确认明细置为待发货，其余明细保持原状态。
2. **Given** 明细已完成标签确认，**When** 业务人员尝试单方面撤回或修改，**Then** 系统拒绝该操作。
3. **Given** 已完成标签的明细确需终止，**When** 业务人员发起取消且标签人员确认，**Then** 系统将该明细或剩余未发数量置为取消状态，并记录双方和原因。
4. **Given** 明细尚未完成标签，**When** 业务人员申请撤回或取消，**Then** 业务人员可以单独执行对应操作；撤回回到草稿，取消直接终止该明细。

### User Story 4 - 仓库分批确认发货（Priority: P1）

仓库按订单明细或整单确认发货。允许一条明细分多次发货，每次发货独立记录数量、物流信息、实际发货时间和操作人员。

**Why this priority**: 仓库需要支持实际交付中的部分发货、多物流号和不同物流公司，同时保证数量和历史记录可追溯。

**Independent Test**: 仓库可以对已待发货明细进行部分发货，填写至少物流公司或物流号之一并明确确认已发货；随后可以继续发剩余数量并查看每次独立记录。

**Acceptance Scenarios**:

1. **Given** 明细剩余 1000 件，**When** 仓库本次确认发货 600 件，**Then** 系统记录本次发货 600 件，明细显示部分发货，剩余 400 件继续待发货。
2. **Given** 明细剩余数量为 400 件，**When** 仓库尝试确认发货 500 件，**Then** 系统拒绝并提示不得超过剩余数量。
3. **Given** 一次发货需要多个物流号，**When** 仓库录入多个物流公司和物流号并确认发货，**Then** 系统保留每个物流信息，不互相覆盖。
4. **Given** 仓库只填写物流公司或只填写物流号，**When** 仓库明确点击确认已发货，**Then** 系统允许完成发货确认；仅填写物流信息但未明确确认时，订单不改变为已发货。
5. **Given** 已发货记录存在物流信息错误，**When** 仓库补填或修改物流信息，**Then** 系统保留修改前后内容、操作人和时间。
6. **Given** 同一 PO 有多次发货，**When** 仓库分别确认每次发货，**Then** 每次发货形成独立记录，包含独立数量、物流信息和实际发货时间。
7. **Given** 发货明细的客户件号未在零件档案中找到，**When** 仓库确认发货，**Then** 系统再次提醒仓库人员确认该件号，且不新增永久异常状态。

### User Story 5 - 查询订单和操作历史（Priority: P2）

业务、仓库、标签人员和管理人员可以查看已提交订单及发货记录。订单详情按时间顺序展示业务操作、标签确认、取消确认、发货确认和物流修改历史。

**Why this priority**: 所有参与人员需要基于同一份订单明细协作，历史记录用于处理异常和追溯责任。

**Independent Test**: 任一已授权角色打开已提交订单，可以看到明细、当前状态、每次发货记录和完整操作历史；草稿仍只有创建人可见。

**Acceptance Scenarios**:

1. **Given** 订单已经提交，**When** 业务、仓库、标签人员或管理人员查询订单，**Then** 四类人员均可查看订单和发货记录。
2. **Given** 订单仍为草稿，**When** 非创建人查询，**Then** 系统不展示该草稿；创建人可以查看和修改。
3. **Given** 订单包含多条明细和多次发货，**When** 用户打开详情，**Then** 系统同时展示明细状态、已发货数量、剩余数量和各次发货记录。
4. **Given** 发货记录需要生产追溯，**When** 用户查看发货记录，**Then** 页面预留生产批次字段；本阶段不要求填写或校验该字段。

### Edge Cases

- 草稿允许暂时不完整，但正式订单提交时必须有客户、PO 号和至少一条完整明细；样件订单不要求 PO 号，但必须有客户或临时客户和完整明细。
- 每条明细必须有客户件号、零件名称、数量、计划发货日期和备注字段；备注可为空，数量必须为正整数。
- 计划发货日期不允许早于当前日期。
- 零件名称默认取零件档案名称，但业务可以修改当前订单明细中的名称；修改不反向修改零件档案。
- 同一客户的同一 PO 号重复创建时，系统提示已有订单及其基本信息，由业务决定取消或继续创建，不自动合并、不强制阻止。
- 同一 PO 可以同时存在已发货、待发货、待处理和部分取消的明细。
- 已部分发货的明细允许取消剩余数量；已发货数量和物流记录不能被取消或删除。
- 已标签明细的取消必须由业务和标签人员双方确认；取消确认后不回到草稿。
- 尚未标签的订单或明细可以由业务人员单独撤回到草稿，或直接取消；已标签的订单或明细不能回到草稿。
- 草稿按最后修改时间保留 7 天；连续 7 天没有修改时自动清除。已提交、已发货和已取消记录不受该清理规则影响。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 支持正式订单和样件订单两种类型，并将正式订单作为新建订单的默认类型；一张订单只能使用一种类型。
- **FR-002**: 正式订单 MUST 要求客户、PO 号和至少一条订单明细；样件订单 MUST 要求客户或临时客户和至少一条完整明细，但不要求 PO 号。
- **FR-003**: 订单明细 MUST 保存客户件号、零件名称、数量、计划发货日期和备注；同一 PO 允许重复添加同一客户件号作为不同明细。
- **FR-004**: 客户件号搜索 MUST 按已选客户过滤，并支持包含匹配、下拉选择和 Tab 补全；系统 MUST NOT 在只有候选结果时自动选中。
- **FR-005**: 客户件号未在零件档案中找到时，系统 MUST 在提交时提醒业务人员，并允许业务人员取消提交或确认继续；仓库发货确认时 MUST 再次提醒该件号未建档；系统 MUST 保留业务输入的原始件号，且不增加永久异常状态。
- **FR-006**: 零件名称 MUST 默认引用零件档案名称，并允许业务人员修改当前订单明细的名称；该修改 MUST NOT 修改零件档案。
- **FR-007**: 计划发货日期 MUST 不早于当前日期；数量 MUST 为大于零的整数。
- **FR-008**: 系统 MUST 在创建相同客户和 PO 号的订单时提示重复信息，并由业务人员决定是否继续；系统 MUST NOT 自动合并或强制禁止重复订单。
- **FR-009**: 草稿 MUST 仅对创建人可见、可修改和可删除；草稿最后修改后连续 7 天未变化时 MUST 自动清除，清除动作 MUST 留有系统日志。
- **FR-010**: 订单提交后 MUST 锁定订单明细，业务人员不得直接编辑；尚未完成标签的订单或明细允许业务人员单独撤回到草稿或直接取消；已完成标签的订单或明细不得回到草稿，也不得由单方取消。
- **FR-011**: 标签人员 MUST 能按订单明细确认标签；部分明细可以先确认，已确认明细进入待发货，未确认明细保持原状态。
- **FR-012**: 样件订单 MUST 不生成全检任务，不要求系统扫码拣货；样件由专人线下拣货后由标签人员确认。
- **FR-013**: 已包装且全检合格的正式成品库存 MUST 支持直接进入待发货路径，不重复全检；具体库存判断和分流规则不在本阶段定义。
- **FR-014**: 标签确认后的明细取消 MUST 要求业务人员和标签人员双方确认，并记录双方、时间和原因；已部分发货时只允许取消剩余未发数量。
- **FR-015**: 仓库 MUST 支持按明细或整单确认发货；整单确认前 MUST 校验所有待发明细，无法整单发货时应改为按明细处理。
- **FR-016**: 系统 MUST 支持一条明细分多次部分发货，并校验本次发货数量不得超过剩余数量；每次发货 MUST 形成独立记录。
- **FR-017**: 仓库确认发货时 MUST 至少填写物流公司或物流号之一，并明确执行“确认已发货”操作后才改变发货状态。
- **FR-018**: 一次发货 MUST 支持多个物流号及多个物流公司；已确认发货后允许补填或修改物流信息，但 MUST 保留修改前后内容、操作人和时间。
- **FR-019**: 发货记录 MUST 保存本次发货数量、物流信息、实际发货时间和仓库操作人，并预留生产批次字段；本阶段不要求生产批次参与校验。
- **FR-020**: 已提交订单及其发货记录 MUST 对业务、仓库、标签人员和管理人员可查看；草稿仍只对创建人可见。
- **FR-021**: 订单详情 MUST 按时间顺序展示创建、草稿修改、提交、标签确认、撤回/取消确认、发货确认及物流修改记录。

### Key Entities

- **订单**：客户一次业务需求的主记录，包含订单类型、客户或临时客户、PO 号、创建人、当前汇总状态和时间信息。
- **订单明细**：订单中的一次计划发货行，包含客户件号、零件名称快照、数量、计划发货日期、备注、标签状态、已发货数量和剩余数量。
- **零件档案**：系统中可查询的客户件号和默认零件名称来源；客户件号与零件名称的档案关系用于搜索和提示。
- **标签确认记录**：标签人员对订单明细完成标签后的确认记录，包含确认人、时间和明细范围。
- **发货记录**：一次实际发货的独立记录，包含订单明细、发货数量、物流信息、实际发货时间、仓库操作人和预留生产批次。
- **物流信息记录**：一次发货关联的物流公司和物流号；同一次发货可有多个物流信息，修改历史必须保留。
- **操作历史**：订单和明细的时间序列审计记录，记录动作、操作者、时间、备注及必要的变更前后内容。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 业务人员可以在 5 分钟内创建并提交一张包含至少 3 条明细的订单，且每条明细的客户件号、名称、数量和日期均可在详情中核对。
- **SC-002**: 对客户件号进行部分字符搜索时，系统只展示当前客户相关候选项，业务人员可以通过下拉或 Tab 完成选择，且不会被系统自动选中错误件号。
- **SC-003**: 仓库可以对一条明细进行至少两次部分发货；系统显示的已发货数量、剩余数量与各次发货记录之和一致。
- **SC-004**: 订单在标签确认、取消确认、发货确认和物流修改后，所有授权查看人员都能看到同一份最新状态和时间顺序操作记录。
- **SC-005**: 草稿最后修改满 7 天且没有新修改后被自动清除；任何已提交订单、发货记录和取消记录不会因草稿清理规则丢失。
- **SC-006**: 样件订单可以不填写 PO 号、使用临时客户，并在不进入全检和系统拣货流程的情况下完成标签确认和仓库发货确认。

## Assumptions and Deferred Scope

- 成品库存的可用量判断、预占、扣减和正式订单在“全检/已有合格库存”之间的自动分流暂不在本规格中定稿。
- 二维码系统落地后的全检任务分配、扫码规则和追溯范围暂不定稿。
- 标签打印内容、标签模板和独立标签流程暂不定稿；本规格只记录标签人员查看明细并确认的业务节点。
- 物流公司接口、电子面单和自动同步暂不包含。
- 退货、冲销和已发货后的逆向流程暂不包含。
- 生产批次字段只预留，不参与当前流程校验。
