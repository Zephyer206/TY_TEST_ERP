# 当前数据库与权威设计差异

> 本文只记录差异，不产生设计决策。目标结构只以 [`../data-model.md`](../data-model.md) 为准。

## 当前结论

当前 PostgreSQL 数据库仍是旧结构和 Excel 直接导入结构的混合体，不能视为目标设计已经落地。

## 核心差异

| 领域 | 当前状态 | 目标状态 |
|---|---|---|
| 客户 | 名称和 Sheet 代号混用，大量 `sheet_key` 为空 | `customers.customer_code` 使用客户名称代号 Sheet 维护 |
| 内部零件 | `parts.part_number` 保存客户件号 | `parts` 只保存内部主档，客户件号进入 `part_customer_aliases` |
| 内部编号 | 客户件号被误当内部编号 | `internal_part_no` 可空，当前不生成 |
| 模具号 | 同时出现在 tooling 和 parts 文本字段 | 统一为 `tooling.tooling_number` |
| 零件模具关系 | 依赖文本模具号，`tooling_parts` 无有效数据 | 使用 `tooling_parts` 外键关系 |
| 模具客户关系 | 单一客户字段或重复模具行 | 使用 `tooling_customer_links` 多对多关系 |
| 非连续模步骤 | “模数”语义混乱 | `process_step_count` + `tooling_steps` |
| 穴数 | 与模数混用 | 只从“1出N”解析到 `cavity_count` |
| 价格台账 | `prices` 与设计中的价格表并行 | 统一 `price_accounts(part_id, customer_id)` |
| Excel 导入 | 固定列号直接写正式表 | 暂存层、动态表头、校验、人工冲突确认 |
| 模具主表 | `tooling`、`dies` 等并行 | 只保留 `tooling` 作为权威主表 |
| 迁移链 | 多个 Alembic head | 收敛为单一可复现迁移链 |

## 已发现的数据问题基线

以下数字来自 2026-07-12 的只读检查，后续清理后应重新生成：

- `parts`：1,534 条。
- `tooling`：1,357 条。
- 表头误导入零件：66 条。
- 表头误导入模具：65 条。
- 空件号零件：32 条。
- 同客户同件号重复：207 组。
- 无零件/模具客户：48 个。
- 无材料关联零件：373 条。
- 无完整 T/W/P 零件：857 条。
- 毛重和净重均只有 10 条有值。
- 文本模具号无法对应模具：171 条零件。
- 160 个多产品模具中，144 个无法通过当前文本关系得到恰好两个零件。
- `tooling_parts`：0 条。

## 迁移阶段

1. 冻结旧 Excel 直接导入脚本。
2. 建立导入暂存和批次追踪表。
3. 清理表头、空件号、错列材料和重复客户。
4. 统一客户代码和正式名称。
5. 将客户件号迁入 `part_customer_aliases`。
6. 建立内部 `parts`，不生成用户可见内部编号。
7. 统一模具主表和模具号。
8. 建立模具步骤、零件关系和客户关系。
9. 对齐价格台账和价格历史。
10. 对齐 ORM、API 和 Alembic 后进行全量验收。

## 完成标准

- 正式表不存在表头和空关键字段记录。
- Excel 源行均能追溯到批次、Sheet 和行号。
- 客户代码无冲突。
- 客户件号映射唯一。
- 零件与模具全部通过外键关系关联。
- 非连续模步数与穴数完全分离。
- ORM 元数据与数据库结构一致。
- Alembic 只有一个 head。
