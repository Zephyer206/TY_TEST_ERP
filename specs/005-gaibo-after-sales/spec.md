# Feature Specification: gaibo 售后统一档案

**Feature Branch**: `005-gaibo-after-sales`

**Created**: 2026-08-17

**Status**: Draft

**Input**: User description: “参考已完成的售后项目，建立 gaibo 售后统一档案；按客户组织单件与安装包，支持全局查询、客户专属图纸与工艺、资料状态、备注和修改历史。”

## User Scenarios & Testing

### User Story 1 - 按客户查看售后档案 (Priority: P1)

售后人员进入售后模块后，以客户作为主要组织方式。每个客户页面同时展示该客户的单件和安装包，用户可以按记录类型、状态和关键词筛选。

**Why this priority**: 客户是售后业务的主要上下文，单件和安装包只是同一客户下的两种记录类型。

**Independent Test**: 创建两个客户工作区和各自的单件、安装包记录，进入任一客户页面，确认只显示该客户数据，并可切换单件/安装包筛选。

**Acceptance Scenarios**:

1. **Given** 系统存在 FMG 墨西哥和客户1两个客户，**When** 用户打开 FMG 墨西哥页面，**Then** 列表只显示 FMG 墨西哥的单件和安装包。
2. **Given** 当前客户同时有单件和安装包，**When** 用户选择“单件”或“安装包”筛选，**Then** 列表只显示对应类型记录。
3. **Given** 客户数量增加，**When** 用户打开售后导航，**Then** 客户入口保持同一套页面结构，不创建客户专属页面副本。

### User Story 2 - 全局售后查询 (Priority: P1)

用户进入“售后查询”后，可以跨客户搜索单件和安装包，并从结果中看到客户、记录类型和核心识别信息。

**Why this priority**: 单件库不是另一份数据，而是跨客户快速定位售后档案的查询入口。

**Independent Test**: 建立来自多个客户的单件和安装包，使用客户件号、IBI、天越内部组成和关键词查询，确认结果可跨客户返回并准确标示记录类型。

**Acceptance Scenarios**:

1. **Given** 多个客户存在相同天越内部组成，**When** 用户在售后查询中搜索该组成，**Then** 返回所有匹配客户记录，并显示客户名称。
2. **Given** 查询结果同时包含单件和安装包，**When** 用户按类型筛选，**Then** 结果只保留所选类型。
3. **Given** 用户从全局查询打开记录，**When** 用户点击结果，**Then** 打开与客户页面相同的详情档案。

### User Story 3 - 建立独立单件档案 (Priority: P1)

用户可以在单件主库中建立一个独立单件，并为不同客户维护不同的客户要求。相同单件可被多个客户使用，但客户件号、IBI、价格、图纸和工艺要求可以不同。

**Why this priority**: 同一个天越单件在客户A和客户B下可能有不同工艺，必须避免用一条全局工艺覆盖所有客户。

**Independent Test**: 建立一个单件并添加客户A、客户B两条需求，分别配置不同工艺，确认两个客户详情互不覆盖。

**Acceptance Scenarios**:

1. **Given** 单件A已建立，**When** 用户新增客户A需求和客户B需求，**Then** 两条需求均关联同一单件主档案但独立保存。
2. **Given** 客户A和客户B对单件A配置不同工艺，**When** 用户分别从客户页面查看，**Then** 每个客户只看到自己的工艺路线。
3. **Given** 单件尚未关联任何客户，**When** 用户从单件主库查询，**Then** 可以看到单件本体并提示尚无客户需求。

### User Story 4 - 管理安装包及其单件组成 (Priority: P1)

用户可以建立安装包，并将已有单件添加为组成；尚未建立单件档案的组成也可以先记录，之后再补建或关联单件。

**Why this priority**: 安装包是客户交付组合，不应复制单件数据，也不能阻塞尚未完成建档的组成件。

**Independent Test**: 建立安装包，添加两个已有单件和一个未建档组成，确认数量、顺序、IBI和天越内部组成均可维护，并可从组成进入单件详情。

**Acceptance Scenarios**:

1. **Given** 客户已有单件档案，**When** 用户将其加入安装包，**Then** 安装包显示该单件及其数量、顺序和客户上下文。
2. **Given** 安装包组成尚无单件档案，**When** 用户保存组成，**Then** 系统允许暂存组成但标记为未关联单件。
3. **Given** 组成件已关联单件，**When** 用户点击组成件，**Then** 打开该客户下的单件需求和工艺详情。

### User Story 5 - 查看和维护客户图纸及工艺 (Priority: P1)

用户点击单件或安装包组成件详情后，可以查看图纸、客户专属工艺路线和详细工艺步骤。工艺以客户和单件为范围，支持版本和生效状态。

**Why this priority**: 客户A需要工艺A、客户B需要工艺B，是售后档案区别于全局产品档案的核心业务规则。

**Independent Test**: 为同一单件建立客户A工艺A和客户B工艺B，分别进入详情，确认图纸和工艺步骤准确隔离并可编辑。

**Acceptance Scenarios**:

1. **Given** 客户A单件A存在图纸和工艺路线，**When** 用户打开详情，**Then** 可以查看图纸版本、工序顺序、工序参数、机台和模具要求。
2. **Given** 客户B对同一单件使用另一工艺，**When** 用户打开客户B详情，**Then** 不显示客户A的工艺作为当前要求。
3. **Given** 工艺已存在历史版本，**When** 用户查看修改历史，**Then** 可以区分当前生效版本和历史版本。

### User Story 6 - 编辑核心信息并保留追溯 (Priority: P1)

用户可以在详情页编辑客户需求、组成明细、图纸、工艺、资料状态和备注。字段显示名称可以按客户配置，但底层核心数据含义保持统一。所有编辑产生修改历史。

**Why this priority**: 业务数据需要随客户确认结果更新，同时必须能追溯谁在何时修改了什么。

**Independent Test**: 修改一条客户需求的价格、工艺和备注，确认保存后新值生效，修改历史记录修改人、时间、字段和前后值。

**Acceptance Scenarios**:

1. **Given** 客户需求已存在，**When** 用户编辑并保存核心字段，**Then** 列表和详情立即展示新值。
2. **Given** 用户将固定字段显示名改为客户习惯名称，**When** 用户查看页面和导出数据，**Then** 页面显示客户名称但系统数据仍能按统一字段查询。
3. **Given** 用户取消编辑，**When** 返回详情，**Then** 原值保持不变且不产生修改历史。

### Edge Cases

- 同一个天越单件被多个客户使用时，客户件号、IBI、价格、图纸和工艺必须按客户分别保存。
- 安装包组成可能暂时没有独立单件档案，但仍必须维护 IBI、天越内部组成、数量和顺序。
- 四个固定核心字段缺失时，新增或保存不能通过：客户件号、IBI、天越内部组成、价格。
- 资料状态可能尚未开始或不适用，不能用空值掩盖实际状态。
- 客户删除或停用时，历史售后档案和修改历史必须保留，不能级联删除业务数据。
- 同一客户同一单件存在多个工艺版本时，只能有一个当前生效版本。
- 同一单件的客户显示名称不同，不得改变统一数据字段和跨客户查询结果。

## Requirements

### Functional Requirements

- **FR-001**: 系统必须以客户作为售后业务的主要组织维度。
- **FR-002**: 系统必须提供“售后查询”全局入口，跨客户查询单件和安装包。
- **FR-003**: 查询必须支持客户、记录类型、客户件号、IBI、天越内部组成、工艺状态和关键词筛选。
- **FR-004**: 系统必须区分单件记录和安装包记录，但不得将二者拆成互不关联的数据体系。
- **FR-005**: 系统必须支持建立独立单件主档案。
- **FR-006**: 一个单件必须可以关联多个客户需求。
- **FR-007**: 每条客户需求必须独立保存客户件号、IBI、天越内部组成和价格。
- **FR-008**: 系统必须将客户件号、IBI、天越内部组成和价格作为固定核心字段，四项均不能为空。
- **FR-009**: 系统必须允许客户配置固定字段的显示名称，但不得改变统一字段含义、查询能力和数据映射。
- **FR-010**: 系统必须支持为客户需求增加客户特有的扩展信息。
- **FR-011**: 系统必须支持安装包引用已有单件，并记录组成数量、顺序和组成状态。
- **FR-012**: 系统必须允许安装包暂存尚未建立单件档案的组成，但必须标记未关联状态。
- **FR-013**: 系统必须支持按客户和单件维护独立的图纸、图纸版本和图纸状态。
- **FR-014**: 系统必须支持按客户和单件维护独立的工艺路线和工艺步骤。
- **FR-015**: 工艺步骤至少必须支持顺序、工序名称、机台、模具、关键参数、质量检查点和备注。
- **FR-016**: 同一单件在不同客户下的工艺不得互相覆盖。
- **FR-017**: 同一客户和单件只能有一个当前生效工艺版本，历史版本必须保留。
- **FR-018**: 系统必须支持图纸、样件、PPAP等资料状态，并记录状态、日期和资料备注。
- **FR-019**: 资料类型必须允许按客户增加扩展项，但公共页面结构保持一致。
- **FR-020**: 系统必须支持详情页编辑主信息、组成、图纸、工艺、资料状态和备注。
- **FR-021**: 系统必须记录所有成功编辑的操作人、时间、字段、旧值和新值。
- **FR-022**: 系统必须支持从客户页面和售后查询入口打开相同的详情档案。
- **FR-023**: 客户停用后，历史档案、图纸、工艺版本、资料状态和修改历史必须可查询。
- **FR-024**: 权限必须至少区分查看、编辑客户需求、编辑工艺、维护客户配置和管理历史数据的能力。
- **FR-025**: 详情档案中展示的业务字段必须可以在详情编辑态修改并保存，包括主信息、四个核心字段、组成字段、图纸/资料状态、工艺字段和备注；数据库主键、创建/更新时间、导入来源元数据和派生统计字段保持只读。

### Key Entities

- **客户工作区**: 售后档案的客户上下文，例如 FMG 墨西哥、客户1、客户2。
- **单件主档案**: 独立维护的天越单件集合，供客户需求和安装包引用。
- **客户需求**: 某客户对某单件的业务要求，包含固定核心字段、客户扩展信息、图纸和工艺引用。
- **安装包**: 客户交付组合，包含多个单件或暂未建立单件档案的组成。
- **安装包组成**: 安装包内的单件引用或暂存组成，包含数量、顺序和状态。
- **图纸版本**: 某客户单件的图纸文件、版本、状态和生效信息。
- **工艺路线**: 某客户单件的生效工艺及其版本。
- **资料状态**: 图纸、样件、PPAP及客户扩展资料的状态和时间记录。
- **备注**: 业务备注、客户反馈和补充说明。
- **修改历史**: 对售后档案、图纸、工艺、资料状态和备注的审计记录。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 用户可以在 3 次点击内从客户入口打开该客户的单件或安装包列表。
- **SC-002**: 用户可以在 10 秒内通过售后查询定位任一客户的单件或安装包。
- **SC-003**: 95% 的全局查询结果在用户提交条件后 2 秒内显示。
- **SC-004**: 用户查看单件详情时，可以在同一档案中看到当前客户的图纸和生效工艺，不需要跨页面拼接信息。
- **SC-005**: 同一单件在两个客户下配置不同工艺后，100% 的客户详情展示各自工艺，不发生交叉覆盖。
- **SC-006**: 新增或编辑记录时，四个固定核心字段缺失的记录 100% 被阻止保存。
- **SC-007**: 100% 的成功编辑都能在修改历史中找到操作人、时间和字段变化。
- **SC-008**: 现有安装包数据迁移后，核心字段、组成、资料状态、备注和历史记录完整率达到 100%。

## Assumptions

- 客户工作区由具有相应权限的管理员维护，客户名称和显示名称不是业务人员随意创建的临时标签。
- 单件主档案可以与现有产品零件建立可选关联，但售后客户需求不依赖全局零件名称才能存在。
- 价格字段在当前 FMG 业务中使用 FCA USD；其他客户可以配置价格显示名称和来源说明，但仍保存为统一价格数据。
- 图纸文件和工艺详细参数由有权限的用户维护，系统保留版本和历史，不自动覆盖旧版本。
- 移动端和客户外部门户不属于第一阶段范围，第一阶段先完成桌面端业务工作台。
- 生产执行记录和实际工艺流转不在本项目第一阶段内；本项目先提供客户需求工艺档案和查询。
