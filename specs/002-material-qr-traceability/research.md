# Research: 产品框二维码追溯扩展

## 范围结论

本次规划针对 `specs/002-material-qr-traceability/spec.md` 中原材料二维码基线之上的产品框扩展：产品二维码池、一框绑定、机台生产、多工艺流转、拆框、卷料规格异常、B/C 转换、追溯和权限审计。现有 US1/US2 原材料入厂与分卷能力视为必须回归的基线，不把 `tasks.md` 中已勾选的旧任务当作本次产品框需求的验收证据。

## 代码基线

- 后端实际目录为 `backend/app`，技术栈为 FastAPI、SQLAlchemy 2.x async、asyncpg、Alembic、Pydantic v2。
- 已有 MaterialBatch、MaterialBatchChild、parent_batch_id、QRScanLog、Machine、ProductionPlan、PlanMachineAssignment、ProductionSession、ProcessFlowCard 和 AuditLog。
- 原材料模型同时保留 MaterialBatchChild 与 MaterialBatch.parent_batch_id 两种父子表达，产品框扩展不应直接复用这两种结构；原材料兼容/迁移另列回归任务。
- 前端使用 Vue 3 + Element Plus，API 以 shared/api/registry.js 为事实源，frontend/src/api/registry.ts 为类型桥接，frontend/src/api/client.ts 统一调用 request client。

## 决策记录

### D1：二维码身份与业务字段分离
二维码 payload 只放版本、类型和不可变身份，例如 `PFB:v1:<pool-item-id>:<public-code>`；客户、订单、产品、数量、工艺等从服务端读取。标签补打只复用原身份，不创建新池项。

2026-10-13 工程基准冻结为 PFB/v1、PFB-创建日-数据库 ID 流水（至少六位）、服务端批量默认上限 500；A4 3×7 通用模板经系统打印对话框选择设备。打印数据发放与用户确认打印分开，物理验收在实现阶段；角色授权待 D-P006。

理由：避免业务字段变更导致标签失效，降低篡改和重放风险，并支持跨工艺沿用同一身份。扫码接口必须校验类型、身份存在、池状态和当前用户权限。

### D2：二维码池与产品框一对一绑定
ProductQrPoolItem 保存唯一编号、生成/打印批次和池状态；ProductBox 保存实物框当前状态。绑定在一个数据库事务内完成，使用唯一约束和行锁保证池项最多绑定一次、产品框最多一个订单。

### D3：数量采用当前值覆盖
框数量保存是幂等的“设置当前值”，不累加历史扫描；每次成功保存写 FlowEvent/AuditLog，带 before_qty、after_qty、版本号。使用 `SELECT ... FOR UPDATE` 或乐观版本号，冲突返回可识别错误，要求客户端重新读取。

### D4：拆框和部分转换使用同一事务
创建子框、绑定未使用池项、扣减父框、建立父子关系和写事件必须原子提交。任一校验失败整笔回滚，父框数量不改变。

### D5：B/C 不建立正式 A 件号
订单直接引用 B 或 C；转换记录保存原/新产品、原订单、原工艺、触发方式和确认人。2026-10-13 FR-033 正式确认：全量转换沿用二维码，部分转换先拆框，子框变更为新产品，父框保留原产品及余量。人工与预授权触发均只先创建待确认记录，操作工确认实际数量后原子提交，不能静默更新产品；取消保留记录且产品/数量不变。

### D6：异常通知采用可替换的站内通知边界
2026-10-13 已确认一期使用 ERP 站内通知/待办，发送失败可重试，投递状态与业务确认独立。采用 Notification/Outbox 抽象，记录收件人、幂等键、投递状态、重试次数和最后错误；工程基准为正常工作器首投递目标 60 秒内、5 次自动尝试，重试按前次失败后 1/5/15/30 分钟，超限保留失败队列和授权人工重试。去重按事件/收件人/渠道，站内待办有唯一来源键。

### D7：审计复用统一 AuditLog，并补充领域事件
关键动作写 AuditLog；产品框业务查询以 FlowEvent、Relation、Exception、Conversion 为结构化事实源。审计记录必须包含操作者、时间、动作、订单/框、前后数量及原因。

### D8：状态值先冻结再编码
2026-10-13 已冻结 FR-031 的业务状态名称与站内通知，技术枚举统一映射到 D-P001；FR-032 已确认生产页面分配、主管/本订单业务人员调整、无额外审批、默认订单优先及数量边界；FR-033 已确认全量沿用原码、部分拆框及操作工实际数量确认。原有三个规格澄清标记全部关闭；订单/路线、打印、角色/收件人及可靠性契约仍属 P0 Gate，不能据此标记生产实现已就绪。

### D9：产出分配以当前可分配量为准
默认订单量取实际可分配量与订单剩余需求中的较小值，余量作备货；授权人员可调整，无额外审批。两项非负整数、合计等于实际可分配量、订单量不超过剩余需求；审计保存操作者和前后值。源数量变更、并发调整与重复提交不能重复占用产出；订单/框级关联结构待 D-P004 冻结。

## 技术研究结论

| 主题 | 选择 | 备选与取舍 |
|---|---|---|
| QR 生成 | 复用 backend/app/services/qr_service.py 与 qrcode[PIL] | 新建第二套 QR 库会增加格式漂移风险 |
| 持久化 | 新增 Alembic 迁移和独立产品框表 | 直接扩展 ProcessFlowCard 会混淆“工艺卡”和“一框身份” |
| 并发 | 数据库唯一约束 + 行锁/版本号双重保护 | 仅靠前端禁用按钮无法防止重复绑定/超卖 |
| 通知 | outbox/站内通知抽象，异常事务内写入 | 直接在请求内调用外部消息服务会造成部分提交和重试困难 |
| 权限 | 复用 `require_role` 和当前登录账号 | 扫描操作工二维码与现有认证模型冲突 |
| 前端 API | shared registry → domain wrapper → request client | 页面直写 axios/fetch 违反 AGENTS.md |
| 测试 | pytest 单元/集成/并发 + Playwright 真实浏览器 | 仅静态检查无法证明现场交互行为 |

## 未解决事项（必须在 P0 关闭）

1. 现有生产计划是否作为“订单”主表；B/C 工艺路线与差异工艺编码、数量分配来源与框级关系。
2. QR 打印/补打授权；编码、上限、编号、A4 通用模板及系统打印对话框工程基准已确定，实物打印仍待实现验收。
3. 主管、业务、生产、仓库、质量的角色级别和跨部门通知收件人。
4. 暂停生产的具体操作影响；通知退避/去重、UTC 毫秒时间、幂等和新领域错误码已由 D-P007 工程确定，仍需实现阶段测试验证。

## 风险缓解

- 需求漂移：用决策记录冻结 P0，并让每个 FR/US 映射到任务和验收案例。
- 数据破坏：只增量新增产品框表；迁移前备份，原材料 QR US1/US2 做回归。
- 重复绑定/数量超卖：数据库唯一约束、行锁、幂等请求键和冲突重读。
- 通知丢失：outbox 状态机、幂等键、重试和后台可查询失败项。
- 标签错印：身份不可变，打印批次可追踪，补打不生成新身份。
- 前端违规：CI 执行 `scripts/check_api_usage.ps1 -FailOnViolation`，新违规数必须为 0。
