# Implementation Plan: 原材料与产品框二维码追溯流转系统

**Branch**: 002-material-qr-traceability  | **Date**: 2026-10-09  | **Spec**: [spec.md](./spec.md)

**Input**: [功能规格](./spec.md)、[技术研究](./research.md)、[数据模型](./data-model.md)、[产品框 API 契约](./contracts/product-box-qr.md)

## 1. 目标与范围

本计划在现有原材料二维码能力之上，实施产品框二维码全生命周期追溯：二维码池批量生成与打印、一框一订单绑定、机台扫码生产、多工艺沿用同一二维码、数量覆盖保存、拆框、卷料规格异常、B/C 产品转换、全链路查询和权限审计。

现有原材料入厂、原材料分卷、机台二维码和工艺流转单能力属于本项目的回归基线。原有 tasks.md 中已完成的任务不能替代本次产品框扩展的验收证据。

本期不扩展物流承运商、客户结算和财务核算；产品 B、产品 C 直接作为业务产品，不建立正式产品 A 件号。

## 2. 技术上下文

**语言/版本**: Python 3.11+；TypeScript；Vue 3

**主要依赖**: FastAPI、SQLAlchemy 2.x async、asyncpg、Alembic、Pydantic v2、qrcode[PIL]、Vue 3、Element Plus、Axios（仅 request client）

**存储**: PostgreSQL，通过现有异步 SQLAlchemy session 和 Alembic 迁移管理

**测试**: pytest/pytest-asyncio；数据库集成测试；并发与权限测试；Playwright 或现有可控浏览器进行真实 UI 验收；前端 vue-tsc、构建和 API 使用扫描

**目标平台**: 现有 Zephyr ERP Web 应用及现场移动扫码场景

**项目类型**: 全栈 Web 应用

**性能目标**:

- 产品框扫码后 3 秒内返回当前数量、订单、产品、工艺和最近事件。
- 任一产品框在 5 分钟内完成订单、工艺、机台、操作工、原材料和转换记录反查。
- 二维码池批量生成、绑定和拆框操作在正常现场负载下完成一次数据库事务。
- 原材料二维码基线继续满足规格中的打印和扫码时限。

**约束**:

- /api/v1 只在现有 request client 中配置；业务代码使用相对路径。
- 新端点必须先登记 shared/api/registry.js，由 frontend/src/api/registry.ts 提供类型桥接。
- 页面和业务组件只能调用 frontend/src/api/ 下的领域模块，不得直接导入 axios 或使用 fetch。
- 关键写入必须在服务层事务中完成，历史事件只追加不覆盖。
- 不输出凭据、数据库密码、SECRET_KEY 或其他敏感配置。
- 涉及 UI 的阶段必须进行真实浏览器验收，代码检查和 API 检查不能替代浏览器验收。

**规模/范围**: 生产现场多角色使用；二维码池支持批量生成；一个订单可关联多个产品框；产品框支持多工艺和父子框关系；预计新增 6 个核心追溯实体及订单分配、机台工艺状态、打印/幂等/outbox 支持记录，约 20 个新 API、2 个主要前端工作区。

## 4. 架构方案

### 后端

沿用 backend/app 的 model → schema → service → api 分层。建议新增 backend/app/models/product_box.py、backend/app/schemas/product_box.py、backend/app/services/product_box_service.py、backend/app/api/product_boxes.py、backend/app/services/notification_service.py 和 Alembic 产品框迁移。

产品二维码池项与产品框分表。二维码只保存版本、类型和不可变身份；客户、订单、产品、数量、工艺等业务字段从服务端查询。绑定、数量保存、拆框和转换均使用数据库唯一约束与行锁/版本号双重保护。

### 前端

建议新增 frontend/src/api/productBoxes.ts、frontend/src/types/productBox.ts、frontend/src/views/product-box-qr/ 和 frontend/src/components/product-box-qr/。shared/api/registry.js 是事实源，frontend/src/api/registry.ts 是类型桥接。

已有原材料、机台和工艺流转端点先做 inventory mapping，再决定复用、补登记、废弃或迁移；不得通过页面硬编码路径绕过 registry。

## 5. 实施阶段

### Phase 0：业务澄清与基线盘点

交付物：决策记录、正式状态字典、角色矩阵、通知方案、QR 编码与打印规则、现有 QR 端点清单、数据库迁移头和回滚方案。

验收证据：spec.md 无 NEEDS CLARIFICATION 残留（原有三项业务决定全部定案）；checklists/requirements.md 需求完整性项通过，其他 P0 条目按 checklists/phase0.md 冻结；原材料 US1/US2、机台 QR、工艺流转现有端点均有回归用例映射。

### Phase 1：数据模型和迁移

新增 product_qr_pool_items、product_boxes、product_flow_events、product_box_relations、coil_spec_exceptions、product_conversion_records；扩展 qr_scan_logs；按 P0 结果建立通知 outbox；增加唯一索引、外键、数量非负约束、版本字段和查询索引。

验收证据：测试库迁移成功；约束和索引可查询；失败迁移可回滚；既有原材料表和 QR 查询无回归。

### Phase 2：二维码池与一框绑定 MVP

实现批量生成、编号、打印数据和补打；池内未绑定二维码绑定一个产品框和一个订单；池外、已绑定、重复订单绑定和产品 A 拒绝；已绑定二维码再次扫码只返回当前框信息。

验收证据：池外/重复绑定 100% 拒绝；并发绑定只产生一个产品框；补打不生成新身份；绑定和扫描审计完整。

### Phase 3：机台生产与连续工艺流转

实现先扫机台再选订单；产品框数量按当前值覆盖保存，不累加重复扫描；再次扫机台表示该订单在该机台完成；差异提示但允许确认；完成后普通操作工不能改数，主管可更正；产品框沿用同一 QR 进入后续工艺。

验收证据：最终值等于最后一次成功保存值；并发冲突返回 409 并要求重读；完成后权限和后续流转符合规格；扫码响应达到 3 秒目标。

### Phase 4：拆框与父子追溯

实现父框扫码、子二维码扫码、数量边界校验和一次事务提交；父框扣减、子框继承订单/件号/客户/后续工艺、父子关系和事件记录；父框余量大于 0 时继续流转或拆分，余量为 0 时禁止继续作为有数量框操作。

验收证据：超量、零量、池外或已绑定子 QR 均拒绝且父框不变；并发拆分不超卖；父子追溯完整。

### Phase 5：规格异常和 B/C 转换

实现规格比较、异常记录、通知 outbox、主管或订单业务人员任一确认；实现 B/C 全量转换保留原二维码，部分转换先拆框，自动触发必须等待操作工确认。

验收证据：异常通知和确认状态准确；通知失败可重试；全量和部分转换记录可追溯；未确认转换不改变产品或数量。

### Phase 6：前端现场工作区

实现二维码池、绑定、机台生产、数量保存、拆框、异常确认、B/C 转换和追溯详情；所有端点先登记 shared registry，再由领域 API wrapper 调用；覆盖扫码错误、权限不足、数量差异和并发冲突提示。

验收证据：前端类型检查和构建通过；scripts/check_api_usage.ps1 -FailOnViolation 新增违规为 0；每个用户故事在真实浏览器中完成并记录浏览器、URL、观察结果。

### Phase 7：联调、回归和上线准备

完成单元、API、数据库、并发、权限、迁移回滚和端到端测试；完成原材料 US1/US2 全量回归；准备监控、审计、通知失败队列、备份、灰度开关、操作手册和培训材料。

验收证据：SC-001～SC-010 全部有测试记录；实现结果与浏览器验收结果分开报告；未通过项目明确标为 incomplete 或 blocked。

## 7. 风险与缓解

- 需求未冻结导致返工：Phase 0 作为硬闸门。
- 旧原材料模型兼容风险：产品框使用独立表；迁移前备份，先跑原材料回归。
- 并发重复绑定或超卖：唯一约束、行锁、版本号、幂等键和 409 冲突响应。
- 拆框/转换双写不一致：父子创建、扣减、关系、事件在一个事务内提交，失败整体回滚。
- 通知丢失或重复：outbox、唯一去重键、重试和失败状态查询。
- 前端接口漂移：registry、领域 wrapper、类型、后端合同和测试同一变更提交。
- 现场扫码重复或网络抖动：接口幂等；客户端遇到冲突必须重读，不静默重放。
