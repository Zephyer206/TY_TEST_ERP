## D-P001：正式状态与通知渠道（FR-031，已确认，2026-10-13）

| 对象 | 已确认显示名称 | 对应技术枚举 | 迁移规则 |
|---|---|---|---|
| 规格异常 | 待确认、已确认 | `pending_confirmation`, `confirmed` | 发现不匹配后待确认；主管或该订单业务人员任一确认后已确认 |
| 处理结果 | 接受继续生产、暂停生产、重新确认卷料 | `accept_continue`, `pause`, `reconfirm_coil` | 与确认状态分列；备注可空，不把通知发送成功当作业务确认 |
| B/C 转换 | 待操作工确认、已确认、已取消 | `pending_operator_confirmation`, `confirmed`, `cancelled` | 待确认不得改产品/数量；确认时原子提交；取消保留历史 |
| 机台订单 | 待生产、生产中、已完成 | `pending`, `in_progress`, `completed` | 状态限定机台/订单/工艺范围；完成不关闭产品框后续工艺 |
| 通知投递 | 待发送、已发送、发送失败 | `pending`, `sent`, `failed` | 异常事务写 outbox；投递与业务确认独立 |

业务回答：“这些我觉得没有问题”，对应上一轮解释末尾明确限定的状态与 ERP 站内通知/待办方案；数量分配及实际转换数量未包含在该回答中。FR-031 已回填。

通知采用站内通知/待办；异常收件人同时包含生产主管和该订单业务人员，双方任意一人确认即可。发送失败保留可查询记录并重试，不能丢弃异常或自动标记已处理。“已确认”仅表示负责人作出处理决定，选择暂停或重新确认卷料不表示规格差异已消除。暂停/恢复的软件行为采用下述 D-P006 设计默认值；技术枚举是业务标签的统一映射，本轮没有修改代码或数据库。

可执行例子：规格不匹配 → 记录待确认异常及两类收件人的 outbox → 业务人员选择“接受继续生产”且备注为空 → 异常已确认并保存确认人/时间；主管再确认不产生第二次业务状态变更。

## D-P002：产出不足时订单量与备货量分配（FR-032，已确认，2026-10-13）

业务回答：“主管或本订单业务人员可调整，无额外审批（推荐）”。FR-032 已回填。

生产工作区设置数量分配入口，默认先满足订单剩余需求，余量作备货；生产主管或该订单业务人员可调整，无额外审批，普通操作工只登记实际产出。订单分配量不能超过剩余需求，两项均为非负整数，合计等于实际可分配数量；不能重复占用同一份产出，保存操作者、时间和前后值，不暗中更改计划量。来源限定首次产出工艺的框，后续工艺不重复计入新增产出；已进入后续工艺、拆框、转换或出库的来源，禁止直接改旧分配，另留更正记录，不改写历史。具体关系见 D-P004 及订单合同。

可执行例子：实际产出 80，订单剩余需求 70、拟备货 20 → 默认订单 70、备货 10；授权人员可调整为订单 60、备货 20。订单 70、备货 20 合计超出 80，或订单分配超过 70，或负数/小数均拒绝。普通操作工调整被拒绝；重复保存不重复分配。

## D-P003：实际完成数量转换（FR-033，已确认，2026-10-13）

业务回答：“采用，全量保留原码、部分拆框并由操作工确认（推荐）”。FR-033 已回填。

全量转换沿用原二维码；部分转换必须先拆框，子框使用池内未绑定二维码，父框保留原产品及剩余数量；无论人工发起或预授权触发，实际完成数量均须由当前操作工确认。原订单、原工艺与转换/父子关系留在追溯链。未确认或取消不改变产品与数量；数量大于 0 且不超过当前值，校验失败整笔回滚。

可执行例子：B 框当前 100，确认转换 100 → 同 QR 成为 C，数量仍为 100；确认转换 30 → 父 B 框 70、子 C 框 30，原订单和原工艺留在追溯链；取消/未确认 → B 框仍为 100。零量、负数、超过当前数量或未提供有效子 QR 的部分转换均拒绝且不改变父框。

## D-P004：订单、工艺路线与跨订单拆框（设计默认值，2026-10-13）

盘点事实：现有 `ProductionPlan` 对应 `production_plans`，`PlanMachineAssignment` 保存计划与机台分配，`ProductionSession` 保存计划、分配、机台、原材料和操作工关系。未发现专用订单业务负责人字段，不能将 `created_by` 自动等同于业务负责人。

采用 `production_plans.id` 作为本期 `order_id`，不新建第二套生产订单。扩展独立二维码订单配置，显式保存业务负责人；未配置时显示“待配置”，不把 `created_by` 当负责人。机台/订单/实际产品/工艺状态独立保存，不覆盖现有计划的全局状态枚举。左右件联合计划绑定时必须选择 `part_id` 或 `paired_part_id` 对应的实际产品及其目标量，不能把一框同时归到左右两件或猜测每件目标量。

按 FR-008 与 FR-019 的共同目的划分拆框：普通拆框和 B/C 部分转换继承原订单；跨订单拆框仅由授权主管或原单业务负责人发起，子框创建时一次性绑定目标单，父框仍属原单。记录来源单、目标单、父子框、数量、操作者和时间；不能改绑已有框。目标单必须有效并允许当前实际产品/工艺，剩余需求充足；不同产品的跨单分配先完成独立 B/C 转换，不能在跨单拆框中跳过操作工确认。目标单客户/件号从目标配置校验生成，来源快照留在关系和事件中。

路线采用有版本的工艺字典及有序步骤；每个订单实际产品配置路线版本和目标量。B 的 1→2→3→4、C 的 1→2→3→4→5 仅为测试示例，不作为真实工艺编码。订单预授权明确来源/目标产品、路线和差异步骤；没有授权只能提示并等待主管/本订单业务发起。默认不允许跳步、回流或覆盖已发生步骤；路线变更只影响新配置，既有框保留原版本及历史。缺路线、产品对应、目标量或机台步骤配置时阻止该项生产写入，返回待配置提示。

产出分配以首次产出工艺的框及数量快照为来源；分配在订单实际产品维度核算剩余需求，排除当前分配后再计算可调整余量。备货分类仍保留来源订单作追溯，不使同一框变成无订单或多订单。一框可记录该单订单量和备货量，两者合计为实际可分配量，不为这两种用途强制另建 QR。普通拆框显式划分父框订单量/备货量；跨单拆框原子转移对应分配，不能再增加一份产出。尚未向下游流转的来源才可调整；有下游事实时返回冲突，改用后续受控更正流程。

来源说明：用户尚未逐项选择上一轮订单问题的选项，本项没有记为第四个已接受回答。以上是依据现有 FR-008、FR-011、FR-019、FR-024 及现有模型所采用的设计默认值，详见 [订单与路线合同](./contracts/order-routing.md)。

## D-P005：二维码身份、编号及打印（工程基准，授权默认值见 D-P006）

2026-10-13 工程选择：产品框独立使用 `PFB` 类型，版本 `v1`，payload 为 `PFB:v1:<pool_item_id>:<public_code>`；解析器单独识别，不能直接交给现有 `prefix:id:timestamp` 解析器。业务字段不写入身份；扫码核对完整 payload 与池项，不能仅信任标签给出的 ID。这是实现约定，不记为额外业务回答。

编号为 `PFB-YYYYMMDD-流水号`，流水采用数据库池项身份 ID、至少六位补零，不按日期复用、不截断长 ID。日期按创建时 Asia/Hong_Kong 计算并持久化，公共编号与 payload 各有唯一约束。单次批量默认上限 500，由服务端配置并校验；补打读取已存 payload，不重新生成带新日期的身份。

默认打印模板为 A4 竖向、3 列 7 行、标签区域 60×35 mm、10 mm 页边距及 5 mm 间距；QR 图形含四模块静区，避免缩放模糊，二维码和唯一编号必印。绑定后可显示授权维护的订单、客户、产品、件号、数量和后续工艺；它们不改变二维码身份。

打印通过浏览器调用系统打印对话框，现场人员选择本次打印机，不写死机器/队列名。2026-10-13 只读设备清单可见本地 PDF 队列，以及重定向的富士施乐/佳能设备队列；队列可见不代表物理连接或打印成功。A4 通用模板为实施基准，现场如使用其他纸张/专用标签机，通过模板配置及对应实物验收处理。

打印数据发放与用户确认打印分开留痕，关闭/取消打印对话框不能记为物理打印成功；补打使用原身份。生成、打印及补打权限采用 D-P006 的显式能力检查，标签实物清晰度和扫码验收在实现阶段执行。详细合同见 [contracts/qr-printing.md](./contracts/qr-printing.md)。

## D-P006：角色矩阵、收件人与暂停范围（设计默认值，2026-10-13）

现有代码等级为 LV1 普通员工、LV2 主管/业务/技术等、LV3 老板、LV4 管理员。等级与部门、订单归属必须联合检查；所有 LV2 不应自动获得生产主管或订单业务权限。

| 业务角色 | 匹配条件与显式能力 | 产品框权限 |
|---|---|---|
| 操作工 | `dept=prod`, LV1+，`qr.production` | 本机有效扫码上下文内绑定、登记/覆盖数量、完成、按路线流转、转换确认/取消；`qr.split` 允许同单拆框；不能改已完成机台数量 |
| 仓库 | `dept=warehouse`, LV1+；按能力授权 | 查询；`qr.bind` 绑定、`qr.split` 同单拆框、`qr.print` 打印/补打；不能作主管更正或跨单分配 |
| 生产主管 | `dept=prod`, LV2+，`qr.supervise` | 分配、跨单拆框、完成后数量更正、异常确认/恢复、发起/取消转换；生成及打印分别需 `qr.generate`/`qr.print` |
| 订单业务人员 | `dept=sales`, LV2+，且为该订单负责人 | 本单分配、跨单拆框、异常确认/恢复、发起/取消转换；`qr.metadata` 可编辑本单标签业务快照 |
| 质量 | 显式 `qr.trace` 授权 | 追溯查询；本期不新增质检结论写入流程，也不以工程部门代替质量部门 |
| 老板/管理员 | LV3/LV4 | 继承现有全局查询范围；只有 LV4 + `qr.admin` 可维护二维码能力/订单配置。业务写入仍需对应能力及订单/扫码上下文，不把管理登录视为操作工实物确认 |

同级非生产/非订单负责人不能越权；部门、最低等级、能力、订单归属和有效扫码上下文必须在服务端联合检查。没有显式授权默认拒绝，本轮不为真实账号发放权限。`qr.metadata` 只改客户显示快照、客户件号及路线允许的后续步骤，不改 QR、订单、实际产品引用或已发生工艺。权限细节和反例见 [权限合同](./contracts/permissions.md)。

通知收件人是已启用 `qr.supervise` 的生产主管集合与明确订单业务负责人，去重后各写一份站内待办。缺负责人/主管时异常照常保存，同时保存待配置收件组；补齐配置后回补投递，不能悄悄丢弃、随机群发或自动确认。未启用代理确认功能，跨部门接收通知不等于获得业务权限。实际账户组只记录部门、等级和数量，不输出个人信息。

暂停默认限定产生异常的机台/订单/产品/工艺生产状态，不扩散到无关机台，也不控制物理设备。`pause` 和 `reconfirm_coil` 保留已确认决定，并阻止该状态新的数量登记、完成及工艺流转；查询、记录异常、取消待确认转换及主管历史更正仍可进行。接受继续生产不阻止登记。主管或原单业务负责人通过独立恢复动作记录复核卷料、处理依据和解除人/时间，保留原决定；未重核卷料不能恢复“重新确认卷料”，新的差异产生新异常。具体合同在产品框 API 中；这是软件处理默认值，不记为用户已明确选择。

## D-P007：通知可靠性、幂等与并发（工程约定已确定，2026-10-13）

- 时间：新事件存 UTC 时间，至少保留毫秒精度，响应为带 UTC 偏移的 ISO 8601，前端按 Asia/Hong_Kong 展示；旧无时区时间列的兼容转换单独验证，不批量改历史。
- 幂等：关键写入使用请求键，按当前登录操作者、动作、实体和规范化请求内容持久化；同键同请求返回原结果，同键异请求为 `409 IDEMPOTENCY_CONFLICT`。业务结果与幂等结果同事务保存，不依赖进程内存，不记录认证头/令牌。并发同键只有一个业务提交，未完成请求不得被当作成功重放。
- 并发：绑定使用唯一约束与行锁；数量、拆框、转换需 `expected_version` 和固定实体锁序，多实体同类锁按 ID 排序；数量按当前值覆盖。版本变化返回 409，客户端重读并让操作工重新确认，不自动重放过期数量。转换确认与取消竞争只能有一个终态。
- 错误：新领域操作统一 `400 INVALID_QR/INVALID_QUANTITY/INVALID_PRODUCT/ORDER_MISMATCH`、`403 FORBIDDEN`、`404 QR_NOT_IN_POOL/ENTITY_NOT_FOUND`、`409 QR_ALREADY_BOUND/STALE_BOX_VERSION/IDEMPOTENCY_CONFLICT/STATE_CONFLICT`。字段缺失和类型验证保持现有 HTTP 422 格式；既有 QR lookup 的 HTTP 200 + found=false 合同保留。
- 通知：工作器正常运行时首次投递目标为写入后 60 秒内；总计最多 5 次自动尝试（首次 + 4 次重试），失败后分别等待 1、5、15、30 分钟，以前一次失败时间为基准。超过上限保留 failed 队列，授权人员可发起人工重试，历史尝试和失败审计保留。事务成功不依赖投递完成，通知失败不替代业务确认。
- 去重：同一异常事件、收件人和渠道各有唯一去重键；重试重用原通知身份，站内投递采用唯一来源键防止重复待办。只有站内通知/待办已持久化才能标记 sent。

这些是授权范围内的可配置工程默认值，不是新增业务回答或外部渠道授权；后续必须用工作器时钟、模拟失败、重放和并发测试验证，尚未实施。已同步模型与合同；暂停软件处理默认值单列在 D-P006，便于后续评审。

## Gate 规则

只有已接受的回答才进入规格 Q/A；本轮仍为三条，不把默认方案补成用户回答。Phase 0 分别检查基线证据、已确认需求、默认方案来源和跨文档一致性。通过表示可以进入后续任务拆解与隔离测试库实施，不表示真实配置或生产验收通过。上线前必须完成真实工艺/差异步骤、左右件目标量、订单负责人、授权账号配置，关闭测试认证绕过，并完成迁移、权限、浏览器及实物标签验收。任何配置缺失不得在运行时通过猜测放行。
